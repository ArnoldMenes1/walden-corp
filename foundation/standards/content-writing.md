# Document 8 — Content & Writing Guidelines

**Version :** 1.0
**Statut :** Document officiel
**Classification :** Fondamental — dépend des Documents 1, 2, 4

---

## 1. Préambule

### 1.1 Rôle de ce document

Le présent document définit les **règles éditoriales** des interfaces Walden Corp. Il précise le ton, le style, le vocabulaire, la micro-copie, les messages d'erreur, les confirmations, les notifications, l'onboarding et l'aide.

Il ne traite pas du contenu marketing (document séparé) mais du **contenu fonctionnel des interfaces**.

### 1.2 Dépendances

- **Dépend de :** Documents 1, 2, 4.
- **Est dépendant de :** Documents 7, 14, 15, 16.

---

## 2. Objectif

Garantir que tout texte affiché dans une interface Walden Corp soit :

- **clair** ;
- **concis** ;
- **cohérent** ;
- **professionnel** ;
- **accessible** ;
- **traduisible**.

---

## 3. Portée

Tous les textes affichés dans une interface Walden Corp : labels, boutons, messages, erreurs, aides, notifications, onboarding.

---

## 4. Définitions

**Micro-copie** — Textes courts fonctionnels (labels, boutons, messages).

**Ton** — Registre émotionnel d'un texte.

**Style** — Manière d'écrire (concision, structure).

**Vocabulaire** — Ensemble des termes utilisés.

**Message d'erreur** — Texte signalant une erreur.

**Notification** — Message signalant un événement.

**Onboarding** — Textes d'intégration.

**Aide contextuelle** — Aide affichée dans un contexte précis.

**Traduisible** — Qualité d'un texte pouvant être traduit sans perte de sens.

---

## 5. Philosophie éditoriale

### 5.1 Postulats

**Postulat 1 — Le texte est une interface.** Un texte mal écrit dégrade l'expérience autant qu'un composant défectueux.

**Postulat 2 — La clarté prime sur l'élégance.** Un texte clair et direct vaut mieux qu'un texte élégant et ambigu.

**Postulat 3 — Le ton est constant.** Le registre ne varie pas selon les écrans.

**Postulat 4 — Le texte est minimal.** Chaque mot doit avoir une fonction.

**Postulat 5 — Le texte est testable.** Chaque texte peut être évalué selon des critères objectifs.

### 5.2 Le ton Walden Corp

Le ton Walden Corp est **professionnel, neutre, direct**. Il n'est ni familier, ni formel à l'excès, ni humoristique, ni marketing.

Il se reconnaît à :

- la concision ;
- l'usage de la voix active ;
- l'usage de la deuxième personne ("vous") ;
- l'absence de jargon interne ;
- l'absence d'emoji ;
- l'absence d'exclamations ;
- l'absence de questions rhétoriques.

---

## 6. Principes éditoriaux

### Principe W-1 — Clarté avant style

Chaque phrase doit être comprise à la première lecture.

### Principe W-2 — ConcisionChaque mot superflu est supprimé.

### Principe W-3 — Voix active

Préférer la voix active à la voix passive.

### Principe W-4 — Deuxième personne

S'adresser à l'utilisateur à la deuxième personne ("vous").

### Principe W-5 — Vocabulaire commun

Utiliser les termes standards du domaine, pas de jargon interne.

### Principe W-6 — Cohérence

Un même concept est nommé de la même manière partout.

### Principe W-7 — Accessibilité éditoriale

Le texte est lisible par tous, y compris par les lecteurs d'écran.

### Principe W-8 — Traduisibilité

Le texte peut être traduit dans toutes les langues supportées sans perte.

### Principe W-9 — Pas d'emoji

Aucun emoji dans les interfaces produit.

### Principe W-10 — Pas d'humour

Aucun humour dans les interfaces produit.

---

## 7. Architecture éditoriale

Le contenu d'une interface Walden Corp s'organise en sept catégories.

1. **Labels** — Libellés de champs, de boutons, de menus.
2. **Messages courts** — Confirmations, avertissements.
3. **Messages d'erreur** — Signalement d'erreurs.
4. **Aides** — Aides contextuelles.
5. **Notifications** — Signalement d'événements.
6. **Onboarding** — Textes d'intégration.
7. **Documentation inline** — Aides longues intégrées.

Chaque catégorie suit des règles spécifiques.

## 8. Standards éditoriaux

**S-W1 — Tout texte est concis.**

**S-W2 — Tout texte utilise la deuxième personne.**

**S-W3 — Tout texte utilise la voix active.**

**S-W4 — Tout texte est rédigé sans emoji.**

**S-W5 — Tout texte est rédigé sans humour.**

**S-W6 — Tout texte est traduisible.**

**S-W7 — Tout texte est documenté dans le glossaire produit.**

**S-W8 — Tout texte critique est validé par un relecteur.**

---

## 9. Règles éditoriales

### 9.1 Règles générales

**R1 — Aucune phrase de plus de 20 mots.**

**R2 — Aucun paragraphe de plus de 4 phrases.**

**R3 — Aucune phrase passive.**

**R4 — Aucun jargon interne.**

**R5 — Aucun emoji.**

**R6 — Aucune exclamation.**

**R7 — Aucune question rhétorique.**

**R8 — Aucun terme ambigu.**

**R9 — Aucune abréviation arbitraire.**

**R10 — Aucun terme anglais non standard.**

### 9.2 Règles pour les labels

**R11 — Un label commence par une majuscule.**

**R12 — Un label ne se termine pas par un point.**

**R13 — Un label est explicite ("Enregistrer le brouillon" plutôt que "OK").**

**R14 — Un label de bouton décrit l'action.**

### 9.3 Règles pour les messages d'erreur

**R15 — Un message d'erreur explique la cause.**

**R16 — Un message d'erreur propose une correction.**

**R17 — Un message d'erreur utilise un ton neutre.**

**R18 — Un message d'erreur ne culpabilise pas l'utilisateur.**

**R19 — Un message d'erreur est associé au champ concerné.**

### 9.4 Règles pour les notifications

**R20 — Une notification informe sans interrompre.**

**R21 — Une notification n'est pas utilisée pour de l'engagement.**

**R22 — Une notification peut être fermée.**

### 9.5 Règles pour l'onboarding

**R23 — L'onboarding est intégré à l'usage.**

**R24 — L'onboarding est facultatif.**

**R25 — L'onboarding ne bloque pas l'utilisation.**

---

## 10. Recommandations

- Lire à voix haute chaque texte pour vérifier la clarté.
- Tester les textes avec des utilisateurs.
- Revoir les textes après traduction.
- Conserver un glossaire produit à jour.

---

## 11. Bonnes pratiques

- Utiliser des verbes d'action.
- Préférer les phrases courtes.
- Être précis ("3 fichiers" plutôt que "des fichiers").
- Utiliser des formats cohérents (dates, nombres, unités).
- Localiser les formats selon la langue.

---

## 12. Mauvaises pratiques

- "Une erreur s'est produite."
- "Voulez-vous vraiment faire cela ?"
- "Cliquez ici."
- "Oups !"
- "Erreur 500."
- "Il y a eu un problème."
- Utiliser "OK" comme label de bouton.
- Utiliser "Annuler" comme label ambigu.

---

## 13. Cas d'usage

### Cas 1 — Message de succès

**Conforme** : "Document enregistré."

**Non conforme** : "Super ! Votre document a bien été enregistré avec succès !"

### Cas 2 — Message d'erreur

**Conforme** : "L'adresse e-mail est invalide. Vérifiez le format (nom@domaine.com)."

**Non conforme** : "Erreur de validation."

### Cas 3 — Confirmation destructive

**Conforme** : "Supprimer définitivement le projet « Facturation » ? Cette action est irréversible."

**Non conforme** : "Êtes-vous sûr ?"

### Cas 4 — Onboarding

**Conforme** : aides contextuelles discrètes, documents courts, exemples.

**Non conforme** : tutoriel forcé au premier lancement.

### Cas 5 — Notification

**Conforme** : "Votre export est prêt. Télécharger." (message discret, fermable)

**Non conforme** : "🎉 Votre export est prêt !" (emoji, exclamation)

## 14. Exemples

### Exemple 1 — Tableau de correspondance

| Situation | Texte conforme |
|-----------|----------------|
| Enregistrer un brouillon | "Enregistrer le brouillon" |
| Supprimer un élément | "Supprimer l'élément" |
| Confirmer une suppression | "Supprimer définitivement ?" |
| Champ obligatoire vide | "Ce champ est obligatoire." |
| Adresse e-mail invalide | "L'adresse e-mail est invalide." |
| Mot de passe faible | "Le mot de passe doit contenir au moins 12 caractères." |
| Erreur serveur | "Le service est momentanément indisponible. Réessayez dans quelques instants." |

### Exemple 2 — Texte long

**Conforme** : "Votre session a expiré. Reconnectez-vous pour continuer."

**Non conforme** : "Désolé, mais il semblerait que votre session ait malheureusement expiré. Pour continuer à utiliser l'application, veuillez s'il vous plaît vous reconnecter à l'aide de vos identifiants."

## 15. Anti-patterns éditoriaux

- **Message générique** — "Une erreur s'est produite."
- **Culpabilisation** — "Vous avez fait une erreur."
- **Humour** — "Oups, c'est cassé !"
- **Marketing** — "Découvrez notre nouvelle fonctionnalité exceptionnelle !"
- **Emoji** — "🎉", "✨", "🚀"
- **Exclamation** — "Bravo !"
- **Question rhétorique** — "Saviez-vous que… ?"
- **Jargon interne** — "Le module ABC-123 est indisponible."

## 17. Critères de validation formels

Un texte est conforme si :

1. Il respecte R1 à R25.
2. Il satisfait S-W1 à S-W8.
3. Il passe la checklist (section 16).
4. Il est relu par un relecteur qualifié.

## 20. FAQ

**Q1 — Peut-on utiliser un emoji dans une notification ?**
Non. Aucun emoji dans les interfaces produit.

**Q2 — Peut-on tutoyer l'utilisateur ?**
Non. Le vouvoiement est le standard.

**Q3 — Peut-on utiliser un ton humoristique ?**
Non. Le ton reste professionnel.

**Q4 — Comment gérer les erreurs techniques ?**
Les traduire en langage utilisateur ("Le service est momentanément indisponible").

**Q5 — Comment gérer la traduction ?**
Utiliser un système de clés i18n, éviter les chaînes concaténées.
